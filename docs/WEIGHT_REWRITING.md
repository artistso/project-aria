# Changing What a Weight Means

> "We have to change the weights — we have to change what it means to be a
> weight — and use our logic here as a rewrite."

That is the right instinct and the hardest possible version of the project. This
document separates what is *literally* possible from what is metaphor, and then
specifies the one mechanism that actually turns ARIA's logic into a weight
change: **the verifier as the reward function.**

---

## 1. What a weight is (and is not)

A weight is a scalar in a parameter tensor. On its own it means nothing. Meaning
lives in *directions* — combinations of thousands of weights that, together,
select a feature — and features are distributed across the network
(superposition). There is no single weight you can point at and say "this one
performs multiplication". So the phrase "change what it means to be a weight"
cannot be an edit to individual numbers; it can only be one of four operations:

| # | Operation | What actually changes | Is it "weight rewriting"? |
|---|---|---|---|
| 1 | **Interface** — grammar, tools, contracts | nothing in the weights; the model's *output alphabet* | no, but it is what makes the channel mathematical |
| 2 | **Training** — SFT, LoRA, RL | the function the weights implement | yes, gradual |
| 3 | **Weight-space editing** — ROME/MEMIT, task arithmetic, merging | specific factual associations / blends of behaviour | yes, surgical, and **not** a path to reasoning |
| 4 | **Architecture substitution** — symbolic layers, hypernetwork-generated weights | what a weight *is allowed to be* | yes, research-grade |

ARIA ships #1 today. This document is about making #2 work, and about why #4 is
the only thing that would literally satisfy "change what it means to be a weight"
— with an honest account of its evidence.

---

## 2. Why weight editing (#3) is a trap here

Model editing techniques (ROME, MEMIT) rewrite a *fact*: "the Eiffel Tower is in
Paris" → "…in Rome". Task arithmetic adds and subtracts *behaviour vectors*:
"more formal + less chatty". Merging blends two models' styles.

None of these installs a *procedure*. Mathematics is procedural: it is the
composition of rewrite rules over many steps. A fact lives in a few MLP rows; a
procedure is spread across attention heads and FFN circuits that route tokens
through intermediate states. You cannot edit `(a+b)^2 = a^2 + 2ab + b^2` into the
weights as a fact and expect the model to then *use* it reliably — which is
exactly the failure mode the whole project exists to fix.

**Conclusion:** skip #3 for competence. Use it only for vocabulary/style drift.

## 3. The mechanism: the verifier is the reward

This is the executable version of "use our logic as a rewrite".

```
   prompt ──▶ model ──▶ contract ──▶ ARIA parser ──▶ engine ──▶ verifier
                          │                                        │
                          └──────── reward ∈ [0,1] ◀──────────────┘
                                        │
                                        ▼
                             gradient step → weights change
```

Every completion is scored by running it through the symbolic runtime
(`aria/llm/dataset.py`):

| outcome | reward | why |
|---|---|---|
| invalid contract (didn't speak mathematics) | **0.00** | fails closed |
| parsed but rejected by the symbolic layer | 0.05 | format right, content unusable |
| `partial` — some steps proven | 0.30 + 0.40 × trace accuracy | provable steps pay |
| `open` | 0.20 + 0.40 × trace accuracy | honest unknown |
| `refuted` | 0.50 | a decided counterexample is a real result |
| `solved` and every step proven | **1.00** | the target behaviour |

Three properties make this a legitimate training signal:

1. **No labels.** The reward is computed from the completion alone. It is not a
   classifier trained on human preferences; it is a decision procedure.
2. **Hard to hack.** To score 1.0 the model must emit a contract that ARIA can
   parse *and* whose every step the verifier proves. There is no paraphrase of
   correctness that earns the reward.
3. **Dense.** `trace_accuracy` gives partial credit per step, which is exactly
   what policy-gradient methods need on long derivations.

What the reward deliberately does **not** measure: whether the model translated
the *right* problem. That is answer quality, measured separately by
`aria bench`, and it stays outside the optimiser so the reward cannot drift.

### The loop

```bash
# 1. pairs: question → contract, generated by ARIA's own parser
aria dataset sft --out data/sft.jsonl --paraphrases 2

# 2. prompts only, with the reward id, for policy-gradient training
aria dataset rl  --out data/rl.jsonl

# 3. score any completion with the verifier (also usable as a TRL reward func)
aria reward --completion "$(printf 'goal: solve\nvar: x\nexpr: 2x + 4 = 10')"

# 4. after training, the same benchmark measures whether it worked
aria bench --json-out benchmarks/post-train.json
```

Reference training scripts (QLoRA SFT and GRPO with this reward) live in
[`training/`](../training/README.md). They need a CUDA GPU; nothing here requires
one.

## 4. Hardware reality (measured from your own device log)

From the Callipeg log on the tablet:

| fact | value | consequence |
|---|---|---|
| total RAM | 11.7 GB | inference only |
| GPU | Mali-G720 Immortalis MC12 (ARM) | no CUDA, no ROCm |
| VRAM estimate | ~2 GB | small-model inference |
| self-reported budget | ~9.4 GB | a 3–4B Q4 model fits |

So: **the tablet runs the channel; it does not train it.** Training tiers:

| model | method | minimum hardware | realistic |
|---|---|---|---|
| 0.6–1.7 B | QLoRA SFT | 1× 16 GB (T4) | yes, hours |
| 3–4 B | QLoRA SFT + GRPO | 1× 24 GB (4090/L4) | yes |
| 7–8 B | QLoRA SFT + GRPO | 1× 40–80 GB (A100) | yes, slower |
| 14–32 B | QLoRA | 1× 80 GB, multi-GPU for GRPO | expensive |
| Kimi K3 (2.8 T) | anything | 64+ accelerators, ~1.4 TB at 4-bit | not for this project |

Iterate on 1.7B. Move up only when the small model has saturated.

## 5. Staged plan, with falsifiers

| stage | action | success criterion | falsifier |
|---|---|---|---|
| **0** | measure the base model on the contract, no training | contract validity rate on 50 prompts | if already >95%, training is unnecessary |
| **1** | SFT on ~2k mined pairs (1.7B, QLoRA) | contract validity ≥ 98%, repairs < 0.2/query | if SFT cannot beat stage 0, the format is too hard for the size |
| **2** | GRPO with `aria.llm.dataset:reward` | solved rate up, invalid derivation rate stays 0 | reward rises while `aria bench` accuracy does not → reward hacking |
| **3** | scale data (10⁴–10⁵ synthetic paraphrases) and model size | generalisation to unseen phrasings | gains vanish on held-out phrasings |
| **4** | rule-conditioned adapters: one LoRA per rewrite family, selected by the contract | measurable per-family accuracy | adapters interfere; merging degrades |

Note the asymmetry that makes this safe: **the reward is a verifier, so a model
that games it has still produced a proof.** Reward hacking here means "the model
learns to ask provable questions", which is the outcome you wanted.

## 6. The literal version: weights as rewrite rules (#4)

If "change what it means to be a weight" means *make the parameters themselves
symbolic operators*, that is a real research direction, not a config file. The
honest map:

| idea | what it would give | state of evidence |
|---|---|---|
| **Symbolic layers** (NALU-style arithmetic units, differentiable logic) | arithmetic that generalises by construction | works on toy arithmetic; does not scale to algebra |
| **Hypernetworks / fast weights** — the model *emits a weight delta* per problem | a literal "rewrite rule applied to the parameter tensor" | real, slow, unstable; no competitive math results |
| **Rule-conditioned adapters** (one LoRA per rule family) | compositional behaviour without retraining the base | promising, cheap, unproven at scale |
| **Continued pretraining on formal corpora + math tokenizer** | weights that natively encode formal structure | the only path with evidence, and it is datacentre-scale |
| **Neural-guided symbolic search** (AlphaGeometry, AlphaProof) | medal-level maths, verified | **works** — but the rules stay *outside* the weights |

That last row is the empirical verdict, and it is uncomfortable: every system
that has actually achieved strong verified mathematics put the symbolic engine
*outside* the model, and trained the model to *propose and translate*. AlphaProof
does this with Lean; AlphaGeometry with a deduction engine; ARIA does it with its
rewrite engine. Nobody has demonstrated that internalising the rules into weights
beats keeping them external.

**Therefore the defensible strategy is inverted from the intuition:** don't
change what a weight means — change what the weights are *for*. Let the weights
do the one thing they are uniquely good at (language ↔ formal notation), and let
the rewrite rules stay where they can be verified.

---

## 7. What would change my mind

Three results would justify moving from #2 toward #4:

1. A rule-conditioned adapter set that matches a single fine-tune on held-out
   problems at <10% of the training cost.
2. A hypernetwork that emits usable deltas for unseen rule compositions.
3. Evidence that a math-tokenizer pretrain beats a same-budget tool-augmented
   model on verified-derivation benchmarks.

None of these exists yet in the literature as far as I can tell. Until one does,
the reward-driven path in §3 is the one that produces real, measurable weight
change in the direction of provable mathematics — and it is the only one you can
run next week.
